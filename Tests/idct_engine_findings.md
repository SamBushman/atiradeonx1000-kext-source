# DVD IDCT engine: what the available evidence says (issue #93)

Question: can the valid path of DVD `doIDCT` (selector 18) be derived from documentation, so a hardware submission can be run under the #87 protocol with evidence-derived parameters?

## 1. AMD document archive (`~/Documents/AMD Docs`, 40+ PDFs converted with pdftotext)
* `R5xx_Acceleration_v1.1-1.5.pdf`, `R3xx_3D_Registers.pdf`: no IDCT or motion-compensation engine section. MPEG appears only as texture formats (`TX_FMT_16_MPEG`), a DAC/colour table row (`C_16_MPEG`) and `MPEG_INDEX` (a packet-index register).
* `RRG-216M56-03oOEM.pdf` (M56 Register Reference Guide, R5xx family) and the RV630/M76/RS690 guides: "IDCT" occurs only as a memory-controller **client name** (`3=idct` in the MC client-select fields, and `MC_WCMB_TIMEOUT` "for these clients only: CP, IDCT, VIP, MCIF"). No register block, no field list, no stream format.
* A search for the registers the kext programs (offsets 0x1f8c, 0x1fa0, 0x1fa8, 0x1fac, 0x1fb4, 0x1fe0, 0x1fe4, 0x1fec, 0x1ff0, 0x1ff8, 0x1ffc) finds none of them in any R3xx/R5xx document. (The Evergreen/Cayman/SI/RDNA/Vega documents are newer architectures with different register maps.)
=> The IDCT engine is **undocumented** in the archive.

## 2. What the shipped kext itself emits (`ATIRadeonX1000::submit_idct_buffer_consumed`, 0x1eb30; `Sources/ATIRadeonX1000_submit_idct_buffer_consumed_Port.cpp`)
Per submission it appends type-0 register-write packets (`0x8000<reg>`, value) to the accelerator ring (`accel+0x91c`, 0x800 dwords, write pointer `accel+0x930`) and then kicks it with an MMIO write to `0x1fa0`:

| register | value (sATIDVDIDCTParams / state) |
|---|---|
| 0x1fe0 | params+0x2c (destination plane start, from the surface plane record) |
| 0x1fe4 | params+0x30 (destination end) |
| 0x1fec | params+0x1c (plane size - 1) |
| 0x1ff0 | params+0x20 (half-height size - 1) |
| 0x1f8c | params+0x10 (`dmaDwordCount`, dwords) |
| 0x1ffc | params+0x24 |
| 0x1ff8 | params+0x28 (pitch, replicated in both halves) |
| (one more dword pair) | `(transferBufferGartAddr + accel+0x8a4) >> 1 & 0x7ffffff0`, then params+0x14 |
| 0x1fa8 | `accel+0x854` (running submission counter) |
| 0x1fac | params+0x18 |
| 0x1fb4 | 0, written six times |
| MMIO 0x1fa0 (kick) | `wptr << 24 | (wptr & 0x700) << 8` |

Only the plumbing is known. What the `dmaDwordCount` words at the transfer buffer contain (the "coefficient/macroblock stream"), what 0x1ffc/0x1fac mean, and what the engine does with a malformed stream are not documented anywhere available. The values in params+0x10..+0x28 are supplied by the VA client (they are not computed by the kext) and point at memory the GPU will read.

## 3. Real-client capture
QuickTime Player and DVD Player (with the passive recorder, `Tools/userspace/va_capture/`) never open a DVD (type 3) connection on this Tiger/X1900 setup; they decode in software. No captured `doIDCT` call exists.

## Conclusion
No documentation and no real-client example gives a valid macroblock stream or valid `sATIDVDIDCTParams` values. A hardware submission would have to use invented addresses and stream content, which the #87 protocol forbids. #93's valid-path phases (A/B) therefore stay unrun; what could change this: (a) a client that actually drives the VA driver (not available here), (b) a captured submission from another OS/driver, (c) AMD documentation of the engine (not in the archive).

# Issue #140 - the engine and its stream, derived (2026-10-04)

(Struct fields were renamed after this analysis: `dmaByteCount` -> `dmaDwordCount`, `chromaFlag` -> `fieldPictureFlag`, `fieldFlag` -> `bottomFieldFlag`, `idctCoeffAddr14/18/24` -> `engineFlagWord` / `planeModeWord` / `dimensionsHeightWidth`; `sATIDVDIDCTInfo` luma/chroma buffers -> stream0/stream1. Section 2's older text still says luma/chroma and byte count - superseded by sections 5-6.)

**Correction to sections 2-3 above.** (a) The doIDCT call site in the VA driver *is* findable: `ATIRadeonX1000VADriver` `FUN_00005fd0` (0x5fd0) calls
`_io_connect_method_structureI_structureO(conn, 0x12, &in, 0x38, 0, &out)`; the selector reaches the wrapper through a register copy that the old
`va_callsites.txt` scan (constant `li r4,N` only) missed. (b) Only part of `sATIDVDIDCTParams` is "supplied by the VA client": `doIDCT` itself computes
+0x1c, +0x20, +0x28, +0x2c, +0x30 (see `ATIR500DVDContext_doIDCT_Port.cpp`). So no live capture was needed: the client *and* a software consumer of the same
data are both present in the stock binaries, and both were read.

Confidence labels below: **EXACT** = read directly from stock code on both sides; **INFERRED** = follows from structure, not stated by any code; **UNKNOWN**.

## 4. What the engine is (external evidence)
* The block is ATI's legacy MPEG-2 hardware decoder at MMIO 0x1F80-0x1FFF. Linux `radeon_reg.h` (also xf86-video-ati, MPlayer vidix `radeon.h`) names
  `IDCT_RUNS` 0x1F80, `IDCT_LEVELS` 0x1F84, `IDCT_AUTH_CONTROL` 0x1F88, `IDCT_AUTH` 0x1F8C, `IDCT_CONTROL` 0x1FBC. vidix's comment describes it as "MPEG-2 hardware
  decoder which incorporates run-level decode, de-zigzag and IDCT into an IDCT engine to complement the motion compensation engine" (`SE_MC_SRC1_CNTL.IDCT_EN`,
  bit 28, is documented as a bare bit in the Rage 128 Pro Register Reference Guide). The ATI Imageon W100 header (`hackndev/linux-hnd`, `drivers/video/imageon/w100/idct.h`)
  gives bitfields for the same family: RUNS = four 8-bit runs per dword, LEVELS = two 16-bit levels per dword, CONTROL = luma/chroma read format, scan pattern,
  intra, flush, passthru, sw_reset, constreq, scramble, alt_scan.
* The Rage 128 Pro RRG (bitsavers `RRG-G04500-C`) lists "iDCT registers" in its chapter overview but contains no register definitions for them; the AMD archive
  (R3xx/R5xx/RV630/M76/RS690/M56) mentions IDCT only as an MC client and a clock-gate bit. **No document defines the 0x1fe0-0x1ffc front end the R5xx kext uses.**
* Consequence (INFERRED): the kext's 11 registers are a DMA front end added in front of the legacy block. Only 0x1f8c overlaps a name in Linux's list (`IDCT_AUTH`),
  and the kext writes `dmaDwordCount` there, so Linux's names are not reliable for the R5xx variant. 0x1fa0/0x1fa8/0x1fac/0x1fb4/0x1fe0..0x1ffc are in no public header.
* Motion compensation is **not** done by this engine on this hardware: the VA driver builds it from 3D-engine quads (`FUN_0000bf20`, command buffer = mapped
  type 1) from the motion-vector lists written by `FUN_00008820`. The engine only reconstructs the residual / intra pixels.

## 5. The doIDCT parameter block (0x38 bytes) - EXACT (client `FUN_00005fd0` + kext)
| off | who | value |
|---|---|---|
| +0x00 | client | 0 for a frame picture (picture_structure == 3), 1 for a field picture. Kext: nonzero doubles the pitch (field access) |
| +0x04 | client | 1 for the bottom field (picture_structure == 2) else 0. Kext: nonzero offsets the destination start by one line |
| +0x08 | client | destination surface index (selects the 0x78-byte plane record) - plane 0 only |
| +0x0c | client | stream/plane selector, 0 or 1; anything else returns 0xe00002c2 **with the accelerator command lock still held** (shipped bug, reproduced) |
| +0x10 | client | stream length in dwords = (write pointer - base) >> 2. **The kext never checks it against the buffer's capacity**; it sizes the CPU cache flush with it and writes it to 0x1f8c |
| +0x14 | client | `0x10080 \| (alternate_scan << 3) \| (plane0 ? 0x20 : 0)`; written as the dword that follows the DMA-address dword in the ring (the `(GART+0x20 >> 1) & 0x7ffffff0` pair, which has no register name in the packet) |
| +0x18 | client | `plane1 ? 0x8000 : 0`; written to 0x1fac |
| +0x1c,+0x20,+0x28 | kext | plane size-1, half-height size-1, pitch replicated in both halves of a dword |
| +0x24 | client | `(height << 16) \| width` in pixels; height is halved unless picture_structure == 3; written to 0x1ffc |
| +0x2c,+0x30 | kext | destination plane start/end |
So 0x1ffc = picture dimensions and 0x1fac = a plane-1 mode bit (0x8000). Meanings of the individual bits of +0x14 beyond alt-scan (bit 3) and "plane 0" (bit 5) are UNKNOWN
(0x10080 is passed unchanged for every call the client makes).

## 6. The two streams - EXACT for layout, INFERRED for semantics
The client maps two kext buffers (`IOConnectMapMemory` types 4 and 5). Each is: 0x20-byte header (`+0x10` = capacity in dwords, `+0x18` = a tag the client stores), data from +0x20.
The kext DMAs from `GART + 0x20`. **Stream 0** carries intra macroblocks (all MBs of an I picture, and the intra MBs of P/B pictures: flag 0x20 above); **stream 1** carries the
macroblocks that have motion (their residual, written to a separate residual surface, `surfaceInfo + 0x8a0`, then combined with the prediction by the 3D engine). That role split is
consistent between the client's routing (`FUN_00003930`: no motion flag -> stream 0, motion flag -> stream 1 + motion lists), the kext's surface choice, and the 0x20 / 0x8000 flags,
but no code states it in words (INFERRED).

Per macroblock that has at least one non-zero block (MBs with six zero counts emit nothing), `FUN_00008510` appends:
* dword 0: `bit31 = field_dct | alt_scan << 25 | CBP << 6`, CBP = six bits (set when that block's count is non-zero), Y0 = bit 11, Y1 = bit 10, Y2 = bit 9, Y3 = bit 8, Cb = bit 7, Cr = bit 6.
* dword 1: `(mb_address / mb_width) << 20 | (mb_address % mb_width) << 4`, address counted within the field for field pictures.
* then the coded blocks' coefficient dwords, verbatim, in block order Y0 Y1 Y2 Y3 Cb Cr, N = sum of the six counts of the host record.
No padding or terminator between macroblocks. (The 0xffff1000 / 0x80000000 / 0xc0001000 pad words seen in `FUN_00007de0` belong to the type-1 command buffer, not to these streams.)

## 7. The coefficient dword - EXACT for the AVA contract (producer `AppleVADriverG5` `FUN_00054070`, consumer `FUN_0000aac0`)
```
dword  = level << 16 | run << 1 | last          level: signed 16 bit, already inverse-quantised; run: 15 bits; last = bit 0
idx    = prev + run;  prev = idx + 1;  block[scan[idx]] = level      (prev restarts at 0 for every block)
scan   = zigzag or alternate, selected by the picture's alternate_scan byte (the producer emits scan *positions*, it never de-zigzags)
```
**Producer** (`FUN_00054070`, the host macroblock decoder in Apple's AVA driver, reached through `AVASliceCreate`; it also writes the 0x1c-byte record: +0x14 motion flags,
+0x15 field_dct, +0x16+blk counts, +0x00..0x0f the vectors):
* intra DC: `dword = ((dc_pred + diff) << (3 - intra_dc_precision)) << 16` (run 0);
* AC and escape levels: `level = ((2*|QF| + k) * W[idx]) >> 5`, sign applied afterwards (`(x ^ s) - s`), `k = 0` intra, `k = 1` non-intra, `W` = a 16-bit table indexed by scan
  position (the quantiser matrix scaled by the quantiser scale, selected per macroblock). That is the MPEG-2 inverse quantisation (truncating toward zero). So the engine receives
  **dequantised** coefficients. No clip to +-2047 and no mismatch-control step was found in this routine - whatever clamping exists is in the IDCT stage;
* **bit 0 = "last coefficient of the block"**: after each block's loop, `if (count != 0) last_dword |= 1`, and the count goes to the record byte `+0x16+blk`.
Both software readers (`FUN_0000aac0` here, and the older `mp2decv` one in section 10) ignore bit 0 because they get the count from the record; the ATI packet has no counts,
so for the hardware bit 0 is what marks block ends.
The host macroblock record the client reads is 0x1c bytes: +0x00..0x0f four (x,y) short pairs = forward MV, backward MV, second forward MV, second backward MV; +0x10..0x13 reference-field
selects; +0x14 motion flags (1 fwd, 2 bwd, 4 second vector; 0 = intra); +0x15 field_dct; +0x16..0x1b six per-block dword counts. Motion vectors are converted to half-pel
(`v - (v>>31) >> 1` plus fraction) for the 3D path, and are never part of the IDCT stream.

## 8. Resolution of the issue's questions
1. Stream format: **derived** (sections 5-7), good enough to build a stream and a parameter block without inventing anything but the pixel content.
2. Fields: 0x1ffc = (height<<16 | width); 0x1fac = plane-1 mode 0x8000; 0x1f8c = stream length in dwords; the (GART>>1 & 0x7ffffff0, +0x14) pair = DMA address and the
   flag word. UNKNOWN: the individual bits of the flag word beyond alt-scan/intra (b0 = last-coefficient flag, resolved in section 7).
3. Why the old capture failed (see section 9): DVD Player's framework decides per display whether to use the accelerator's own VA driver or its built-in AltiVec software
   driver, and on this machine it never picks the former. The software renderers consume the same macroblock records and coefficient dwords, which is why they are the best
   available specification of the stream.

## 9. Why no player ever opens a DVD context on this machine (and what that means for a capture)
* The accelerator does publish the hook: `ioreg` on the G5 shows `IODVDBundleName = "ATIRadeonX1000VADriver"` (and `IOGLBundleName = "ATIRadeonX1000GLDriver"`).
* `DVDPlayback.framework` (`FUN_98250298` and three near-copies) enumerates the displays, reads that property, and loads the named bundle - but it substitutes the literal
  string `AppleAltiVecDVDDriver` whenever a local flag is set: `(DAT_a8178510 || DAT_a8178511 || !hw_check_passed) && display_uses_OpenGL_acceleration`. `FUN_9824f580` is the
  setter for the two flags; the hardware check is a function pointer loaded from a separate bundle that was not identified. The binary contains a short GPU name list
  (`NVIDIA GeForce FX 5200`, `NVIDIA NV34MAP`, `ATI Radeon 9600`, `ATI Radeon 9600 XT`); the Radeon X1900 is not on it. I did not prove that this list is the gate - only that
  it exists next to the gate and that the observed behaviour (software on the X1900) fits it. (INFERRED)
* Consequence: a capture of a stock player on this GPU will not be obtained by playing more content. Either the gate has to be satisfied (not attempted), or a purpose-built client has to call
  the VA driver, which the derived format now makes possible without guessing the stream.

## 9b. Live capture from the real VA driver (rung 2, 2026-10-04) - confirms sections 5-7 with real data
Method: `Tools/userspace/va_capture/ava_drive.c` drove Apple's own `AppleVA` entry points (`DVDDriverOpenDeviceImpl` / `DVDDriverDecodeImpl`, which load and call the real `ATIRadeonX1000VADriver` through its AVA 1.2 table) under the default-deny shim `iokit_guard_va.dylib` (doIDCT,
every command-buffer re-map and every stream re-map swallowed; nothing reached the engine). Three pictures (two I, one P; 64x48) with a known content were built from `Tools/idct_stream.py` in the DVD-driver coefficient layout. `compare_guard.py` checked the capture against predictions made *before* the run:
* all 4 `doIDCT` parameter blocks match on every client-written field: fieldPictureFlag/bottomFieldFlag 0 (frame), destPlaneIndex = destination surface, planeSelector 0 for intra MBs (also the intra MB of the P picture) and 1 for the forward-predicted MB, `dmaDwordCount` 19/9/3/3 (dwords),
  `engineFlagWord` `0x100a0` (intra, zigzag) / `0x100a8` (intra, alternate scan) / `0x10080` (stream 1), `planeModeWord` `0x8000` for stream 1 only, `dimensionsHeightWidth` `0x00300040`;
* all 34 stream dwords captured from the type 4/5 buffers equal the predicted packets (macroblock header dwords, CBP bits, MB row/column, run/level dwords with the last-flag, block order): this validates AppleVA's in-place conversion from the DVD-driver layout (`FUN_97d83730`), the ATI client's packet writer (`FUN_00008510`) and the stream routing;
* the client leaves +0x1c/+0x20/+0x28/+0x2c/+0x30 uninitialised (stack residue such as "ATIVADri") - the kernel computes them; confirms the kext/client split in section 5;
* stream buffer header: `+0x10 = 0x0001fff8` (capacity in dwords: a 0x80000-byte buffer minus the 0x20-byte header), `+0x1c = 1`; data starts at +0x20.
Real set-up sequence the driver uses (forwarded calls, all returned success on the stock kext): `IOServiceOpen` type 3; selector 1 `get_config` (out `0x810040, 0x10000000`); `IOConnectMapMemory` type 1 (command buffer, 0x80000), type 4 and 5 (IDCT streams, 0x80000 each), type 2 (0x1000);
`set_surface(sid, 0x4000, 1)` where `sid` is the WindowServer surface id from `CGSAddSurface` (bound through `CGSBindSurface`); `setup_buffers(0, 0x40, 0x30, 0, 0x27c00)` (width, height in pixels, then a size) and again with `0x37c00`; then 17 `declare_image` calls (selector 8, in = 0, a 256-byte-aligned CPU address, a size; out = a pointer
the driver dereferences and increments) and at close one `delete_image` (selector 9) per image. A 2D connection is also opened and used (selectors 1, 0) by the display extension. The DVD context was released cleanly on close in every run.
Lesson recorded in the shim: a swallowed `declare_image` must hand back a valid private block (a zero crashed the harness, SIGBUS in `FUN_00003cd0`; the kernel was unaffected and released the context). Five real DVD command-buffer snapshots (type 1) were also captured and can be pushed through `kemu.py` safely.
What this does NOT show: any behaviour of the engine itself (nothing was submitted); the open hardware questions in section 10 stand.

## 9c. Rung 3a: the first forwarded doIDCT on the stock kext (2026-10-04) - declined with NotReady, engine untouched
Setup: the rung 2 harness with `GUARD_FORWARD=18` (write-ahead log fsynced before the call), one picture (`R3a`: one intra macroblock, DC-only Y0 = 1024, 3 stream dwords, destination index 0, 64x48), window at (800,500); #87 preflight/peer-ack, log mirrored to the dev machine, IDCT register block snapshot before/during/after (read-only through the 2D `read_regs`).
Result (run `r3b`): the kernel returned **`0xe00002d8` (NotReady)** after ~14 ms. Nothing was submitted: during the hold every engine register except the start-up ones is unchanged, the kick register `0x1fa0` and the stamp `0x1fa8` still read 0, the ring pointers `0x1f9c`/`0x1fa0` are 0, and after exit all 17 originally-sampled registers equal the pre-run values. The harness completed, the DVD context was released, no stray process, nothing in `system.log`. (Postflight flagged one extra "Error detected (-9972) while verifying/repairing volume" line for the in-use boot volume; the check lines are otherwise identical, including the pre-existing live "Volume Bit Map needs minor repair"; judged a mounted-volume verification artifact, not damage.)
Outcome class: EXPECTED-REJECT-class (the body can return this code), but the *reason* is not established. What the evidence says:
* The XDCT ring front end IS started when a DVD context opens (`ATIR500DVDContext::start` -> `start_xdct_engine`, which sets `accel+0x8bc = 1`): with a context open `0x1f94` reads `0x2002030a` (what `start_xdct_engine` writes; idle: `0xa802030a`), `0x1f80` reads `0x8005000a` (idle 0; same in a run where doIDCT was swallowed). Ring base `0x1f90 = 0x10003000`, read-pointer write-back address `0x1f98 = 0x10000004`, read/write pointers `0x1f9c = 0x1fa0 = 0`: an empty, plausible ring. `0x1fc0-0x1fdc` change between reads (volatile, meaning unknown). So the "IDCT-enabled" and "ring has space" conditions look satisfied.
* (SUPERSEDED by the rung 3b analysis below, which weighs the timing evidence) First hypothesis: `doIDCT`'s destination base `params+0x2c` (the surface plane record `surface + destIdx*0x78 + 0x558`, i.e. `shape_surface` slot 10 + index, the "overlay" slots) is zero for the WindowServer-created surface, so the submit block is skipped (`if (params+0x2c != 0)`) and the call returns NotReady. Not proven: the other NotReady exits (no bound surface, accelerator not up, tag check) are excluded only by inference. The ~14 ms is unexplained (other forwarded calls in the same log take up to ~5 ms).
* Where overlay slots come from is not established. The VA driver never calls selectors 10/11/12 (`show_buffer`, `dvd_setup_overlay`, `dvd_enable_overlay`) - its kernel calls are 0, 1, 4, 8, 9, 17, 19, 20, 21 and 18 only - so in the real DVD Player flow the surface must be shaped with overlay slots by the WindowServer's bind (`CGSBindSurface`) or by something the harness does not do (surface bounds / window state).
**Rung 3b static analysis (2026-10-04; revises the inferred cause above).** Reading the kernel side end to end:
* `IOATIR500DVDContext::set_surface` finds the surface by id (our WindowServer surface id works), ORs `0x400 << i` for `i < flagCount` into the context's slot mask (`this+0x88`), calls `surface->set_dvd_context(this)` (which sets `surface+0x90 = this` and ORs the mask into the surface's gate bits `surface+0xc18`) and `prune_buffers()`. `setup_buffers(0, w, h, 0, mask)` stores the rect at `surface+0x94..0x9a` and *replaces* the context mask with `(mask & ~0x3ff) | 0x20000002`; the driver's masks are `0x27c00` then `0x37c00` = slots 10-14, 17 (then 16 as well), followed by another `set_surface`. `prune_buffers` zeroes every slot whose gate bit is clear and keeps the others, then calls vtable `+0x5c8`; `shape_surface` pass 4 (slots 10-22, gate bits `0x7ffc00`, only when `surface+0x90 != 0`, geometry from the rect) allocates them. So by this reading the destination slots (`doIDCT` uses slot `10 + destIdx` for stream 0, slot 17 for stream 1) *are* requested and created by the driver's own sequence - the "empty destination" explanation is therefore **not** well supported (it remains possible if `shape_surface` aborts early).
* Timing contradicts a quick early return: every other kernel call in the capture takes ~25 us, `doIDCT` took ~14 ms. 14 ms is what the 1,000,000-iteration free-space spin in `submit_idct_buffer_consumed` costs on this CPU (each iteration reads a 16-bit value and increments a static up to 16 times) - and the spin timing out explains why the ring and kick registers never moved. The other deep candidate is the first-use `map_transfer_to_GART` of the 512 KB stream buffer.
* That free-space check has two modes chosen by `accel+0x98 & 0x80000`: read the engine's read pointer from MMIO `0x1f9c`, or read a 16-bit value from the shared status page at `+4`. The chip-family table in `ATIRadeonX1000::start` sets `0x110000` (device ids 0x7100-0x710f), `0x410000` (0x7140-0x7157, 0x715e), `0x210000` (0x71c0-0x71de) or `0x810000` (0x7240-0x724f, 0x7260-0x726f: the X1900/R580 case) and **never** `0x80000`, so every supported chip uses the status-page mode; the observed `0x1f98 = 0x10000004` (write-back address = status page + 4) agrees. The value there is written by the hardware only when it updates its read pointer; its initial content is whatever the status page held. A stale or unwritten value that makes `(value - wptr - 1) & 0x7ff < 0x20` would stall every first submission - consistent with the observation, but it needs 1/64 of 16-bit patterns (values 1..32) or a non-zero software write pointer, so this is a plausible, not a certain, explanation.
* Two discriminating live checks, both on already-seen code paths and neither able to start the engine: (1) the same forwarded `doIDCT` twice in one context - if the first call paid for `map_transfer_to_GART` the second is fast, if it is the spin both take ~14 ms; (2) a forwarded `doIDCT` whose destination index has no slot (index 5 -> slot 15, outside the mask): that must return NotReady in microseconds before touching anything and gives the baseline for "quick early return".
Side findings: the IDCT block is a real ring-driven front end (`start_xdct_engine`: base 0x1f90, control 0x1f94, read-pointer address 0x1f98, read pointer 0x1f9c, write pointer 0x1fa0, stamp 0x1fa8, run control 0x1f80) - see `ATIRadeonX1000_Xdct.cpp`; this refines section 2's table (0x1fa0 is the ring write pointer, not only a "kick").

## 9d. Rung 3: the engine runs (2026-10-04) - first real hardware submission, accepted and consumed
**Why the first attempt was declined (resolved).** Timing re-measured with the guard timing only the kernel call: a forwarded `doIDCT` takes 12-14 us whether the destination index is 5 (no slot) or 0, twice in a row - the earlier "14 ms" was entirely my own write-ahead logging (snapshot + fsync), so there was no deep path and no ring spin. Both calls were quick early exits at the `dest base == 0` check. The destination slots are not built by `set_surface`/`setup_buffers`: they are allocated by `Surface::alloc_surfaces`, which runs inside `lock_all_buffers` (selector 4) and in `clientMemoryForType`'s command-buffer re-map (type 1 re-map; swallowed by the guard). The VA driver calls selector 4 only in the tail of its set-parameter function (`FUN_00002e50`, after selectors 0x15 and 0, when a post-processing effect flag is set); my harness never did, so the slots stayed empty. After a forwarded selector 4 (`--lock-buffers`, same sequence as that tail), the kernel returned real slots: 5 buffers (slots 10-14, pitch 0x100, e.g. 0x08e18000..), slot 16 (pitch 0xc00), slot 17 (the stream-1 residual slot, pitch 0x200) and zeros for the unrequested slots 15 and 18-22, exactly the requested mask.
**The submission (run `s1`, forwarded selectors 4 and 18, picture `R3a`: one intra macroblock, DC-only Y0 = 1024, 3 stream dwords, 64x48, destination slot 10).** `doIDCT` returned `rc = 0` (kernel call 308 us). The IDCT block's registers afterwards (read-only snapshot during the hold, identical 5 s later; the same state as the dry-run model predicted): `0x1f8c = 3` (dmaDwordCount), `0x1f9c = 0x20` and `0x1fa0 = 0x20` (the ring read and write pointers both advanced by the 32 ring dwords: **the engine consumed the whole ring**), `0x1fa8 = 1` (the stamp the ring writes), `0x1fbc = 0x000100a0` (the client's flag word, i.e. **`engineFlagWord` is written to `0x1fbc`, Linux's `IDCT_CONTROL`; its bit 5 = intra agrees with the ATI W100 header's `idct_ctl_intra`**), `0x1fe0/0x1fe4 = 0x08ed0000/0x08ed3000` (destination start/end = slot base and base + 48 lines x pitch), `0x1fec = 0x2fff` (pitch*48-1), `0x1ff0 = 0x17ff` (pitch*24-1), `0x1ff8 = 0x01000100` (pitch in both halves), `0x1ffc = 0x00300040` (height<<16 | width). Teardown clean: harness exit 0, DVD context released, nothing in `system.log`, no crashdump, all sampled registers back to their pre-run values, #87 postflight rc 0 (volume checks identical).
**What this does and does not establish.** Established: the engine is present and runs on the X1900 under the stock kext; a valid, derived stream (macroblock header + run/level dwords with bit 0 set on the last coefficient) is accepted and the ring is consumed without a hang or fault; the register-level behaviour of the kext's submission is as derived. NOT established: what the engine *wrote*. The destination is off-screen video memory (slot 10 at a VRAM offset) and no read-back path has been built yet, so the pixel questions (DC scaling/clipping, bias, alt-scan orientation, block order, stream-1 sign, the effect of bit 0) are still open. A missing end-of-block bit was not tried (it is the case most likely to stall the engine).

## 9e. Rung 3: the engine's output observed (2026-10-04)
**Read-back path (new).** The destination VRAM is not CPU-visible (slot addresses are ~142-150 MB; the CoreGraphics aperture mapping stops at 128 MB, `vram_peek`), and GL `read_buffer` reads surface slots 0/1/4/5 only. `doIDCT` takes its destination index straight from the client and computes the record as `surface + idx*0x78 + 0x558`; index `-10` (0xfffffff6) lands on the surface's own slot 0 record (`surface + 0xa8`), a valid in-object record (a read of it; nothing outside the object is touched). With the destination set to slot 0 and the proven read path (a 2D client binds the surface and `lock_memory(0)`/`unlock_memory(0)` creates the backing memory, then a GL client bound to the same surface issues `read_buffer` with `sourceSelector 1` = slot 0, as in `t3_gl_read_buffer`), the engine's writes can be read back. Controls: the read is byte-identical across repeats when nothing is decoded (`ctl`, 12,288 bytes x3).
**Result (run `px4`: forwarded `doIDCT`, destination slot 0, picture `R3a` = one intra MB, Y0 DC-only level 1024, other blocks uncoded; kernel call 313-319 us, rc 0).** Registers as in 9d with `0x1fe0/0x1fe4 = 0x09320000/0x09323000` (slot 0's base and base + 48 x 0x100). The 64x48 slot-0 read differs from the control in exactly **64 pixels = 256 bytes = one macroblock of luma**, stable 3 s later. Per 16-byte group (one MB luma row): `ff ff ff ff ff ff ff ff 00 00 00 00 00 00 00 00` - the coded block Y0 row saturated at 0xff, the adjacent *uncoded* block Y1 row written as 0x00. All 16 groups are identical in content and are scattered over four memory rows (0, 4, 8, 12 in memory order, bottom-up in the GL read) at x offsets {0,16,32,48} and {8,24,40,56}: the engine wrote 16 linear rows of 16 bytes at pitch 0x100 and the window surface is *tiled*, so the de-tiled GL read shows them spread out. (The 64x48 window buffer's own content is ~12,200 non-zero bytes of unrelated window pixels; only the differences matter.)
What this establishes: the engine really decodes the stream and writes a 16x16 luma macroblock to the destination; uncoded blocks of a coded macroblock are written as zero (the macroblock is overwritten as a whole); the destination is addressed linearly from the base with the given pitch. What it shows against my oracle: **DC level 1024 gave 255, not 128** - the engine's gain on a DC-only block is at least 2x the standard IDCT's (the scale, or the level convention, differs). Not yet known: the exact gain (needs unsaturated levels), the tile map (needs distinct values per row/column), chroma placement (chroma was deliberately left uncoded: the destination end register bounds the region to the luma plane and a chroma plane beyond it must not be driven until its placement is understood).

## 9f. Rung 3: the engine's numeric behaviour measured (2026-10-04; run `pb1`, picture `R3b`)
Probe: one intra MB, Y0 = DC 64 + zigzag idx 2 (40), Y1 = DC 64 + idx 1 (40), Y2 = DC 32 + idx 2 (40), Y3 = DC 96; destination slot 0 read back as in 9e (`Tools/userspace/va_capture/decode_px.py` reconstructs the macroblock from the before/after dumps).
* **Output = the standard MPEG-2 IDCT of the levels, + 128, clipped to 0..255** (for stream 0 / intra). Y3 (flat, DC 96) reads 140 = 128 + 96/8; the earlier DC 1024 read 255 = clip(128 + 128). Against the oracle (IDCT + 128, clip; uncoded blocks 0) the 256 luma samples agree exactly in 239 cases and differ by +-1 in 17 (fixed-point rounding), worst |diff| = 1. So the levels are used as given (already dequantised, no extra gain) and the oracle in `Tools/idct_stream.py` is correct up to +-1.
* **Scan:** with the picture's alternate-scan flag clear, coefficient index 1 is the horizontal frequency and index 2 the vertical one (zigzag), exactly as the oracle's scan table.
* **Block placement:** Y0 top-left, Y1 top-right, Y2 bottom-left, Y3 bottom-right of the macroblock (frame DCT layout).
* **Uncoded blocks of a coded macroblock are written as 0** (not left untouched, not 128).
* **Read-back geometry (properties of the tiled window surface and its aperture, not of the engine):** each 32-bit word is byte-reversed in the read-back; the 16 linear luma rows r = b3b2b1b0 of macroblock (0,0) appear at memory row `4*(b0 xor b1) + 8*(b2 xor b3)` and pixel x `16*b1 + 32*b3 + 8*(b2 xor b3)` (memory row = 47 - GL row), i.e. a Gray-like bank/pipe swizzle of the linear address bits 8-11. Only macroblock (0,0) was used so far; positions of other macroblocks are not yet calibrated.
* Open: alternate scan, run lengths > 0 and the end-of-block flag semantics, level clipping/negative levels, field-DCT line interleave, CBP subsets, chroma (not driven: the destination end register bounds the luma plane and chroma placement is unknown), stream 1 (its destination is the fixed slot 17, not readable through the slot 0/1 read path).

## 9h. Rung 3: the control word (`engineFlagWord` -> IDCT_CONTROL 0x1fbc) decoded by clearing its bits (2026-10-04; runs `fl20`, `fl80`, `fl10000`, `alt1`)
The client sends `0x10080 | alt_scan << 3 | (stream 0 ? 0x20 : 0)`. With the guard's `GUARD_FLAG_CLEAR` knob (clearing only, never setting) on the zigzag probe picture:
| bit cleared | observed effect |
|---|---|
| 0x20 (bit 5) | **Intra vs non-intra mode.** Cleared: no +128 bias, no 8-bit clip, samples are **16-bit signed** values (Y0 rows read 15, 14, 12, 9, 7, 4, 2, 1 = the biased values minus 128, in 32 sixteen-byte groups instead of 16: two bytes per sample). Set: 8-bit pixels, +128, clipped to 0..255. Stream 1 (residual) therefore produces 16-bit residuals - consistent with its slot's pitch 0x200 vs 0x100 for the intra slots. |
| 0x80 (bit 7) | Normal layout needs it set. Cleared: the **first coded block's coefficients land two scan positions later** (the DC level 64 appears at position 2 = vertical (1,0), the AC level 40 at position 4 = (1,1)); Y1-Y3 unchanged. (Likely a "first block / header" handling bit; semantics beyond this effect unknown.) |
| 0x10000 (bit 16) | Cleared: output **exactly equals the oracle (256/256)**; set: +-1 differences in about 17 of 256 samples. Bit 16 enables a dither/rounding variation. |
| 0x08 (bit 3) | Set = alternate scan (run `alt1`, matches the alternate table). |
So the control word is: bit 3 alternate scan, bit 5 intra (8-bit biased/clipped pixels vs 16-bit residuals), bit 7 required (first-block position handling), bit 16 dither/rounding, other bits as in the client's value (0 elsewhere). The oracle matches the engine exactly when bit 16 is clear.

## 9i. Rung 3: end-of-block semantics (2026-10-04; run `last1`, picture `R3b` with every last flag cleared)
`GUARD_CLEAR_LAST=1` cleared bit 0 of every dword in the stream buffer (the guard edits the mapped buffer just before forwarding). Result: **no hang, no fault** (rc 0, 313 us, ring consumed, postflight rc 0). Output: block Y0 now contains the sum of *all* eight coefficients of the stream (a complex pattern: Y0's DC 64 and idx 2, then the run/level pairs of Y1, Y2 and Y3 accumulating positions), and Y1, Y2, Y3 are zero. So: **block boundaries are marked only by the last flag**; the six CBP bits say which blocks follow and in what order, not where they end; without flags the first coded block consumes every dword up to the DMA length (`dmaDwordCount`) and the remaining coded blocks receive no data (written as zero). A stream without end-of-block flags is therefore harmless to the engine (bounded by the DMA length) but decodes wrongly.

## 9j. Rung 3: macroblock addressing (2026-10-04; runs `pos1`, `pos4`, pictures `R3g`, `R3h`)
The same probe macroblock at macroblock address 1 (row 0, column 1) and address 4 (row 1, column 0) of the 64x48 picture; `locate_px.py` matches each changed 16-byte group to the luma row it carries. All 16 groups are found with the expected values in both runs, so **the engine writes the macroblock at the position given by the header's second dword** (`row << 20 | column << 4`): column 1 = +16 bytes and row 1 = +16 lines (+0x1000 bytes at pitch 0x100) in the linear destination. In the tiled window read-back, column 1 appears exactly one memory row lower with identical x offsets, and row 1 appears 16 rows lower with the group x offsets permuted by the same address-bit XOR swizzle as at (0,0) - consistent with a linear-address-to-tile function on the window surface, not with anything in the engine.

## 9k. Chroma attempt (2026-10-04; runs `chroma1`, `chroma2`, picture `R3i`, `--height 32`): not observable through slot 0
Idea: with the DVD rectangle height 32, luma is `0x2000` bytes (32 x 0x100) and the chroma plane, if it starts at the end register `0x1fe4` (= luma end) with size `0x1ff0 + 1` (= half the luma size), would fall at `+0x2000..0x3000`, inside slot 0's 48-line buffer. Result: `rc = 0`, the luma macroblock is exact (136 flat, 256/256), and exactly 256 bytes changed in the whole read - **no chroma bytes anywhere in the readable slot**. Cause found afterwards: attaching the DVD context with a custom window rectangle (`setup_buffers`) reshapes slots 0/1 to that rectangle (`shape_surface` pass 3 with `surface+0x90 != 0`), so the readable height of slot 0 became 32 rows (the `--readall` run shows the last 16 rows of the 48-row read untouched) and the chroma area lies below the readable rows - and probably beyond the reshaped slot-0 allocation, so this probe may have written up to one chroma plane's worth of bytes (a few hundred bytes) into memory that is not slot 0. No damage was observed (display, `system.log`, postflight regs), but the approach is not clean and was stopped. The other GL-readable slots (selectors 0, 2, 3, 4, 7, 8, 10, 11 -> slots 1, 4, 5, 6, 2, 3, 7, 8) all returned CannotLock (not allocated), so the stray chroma cannot be searched for there. A clean chroma test needs a destination that is NV12-sized and owned by the test (a DVD slot 10-14) *and* a way to read it back, which does not exist yet (the slots are above the 128 MB CPU aperture; `/dev/mem` on the video BAR is the same class of access that crashed this machine earlier and is not used). ## 9l. Chroma observed end to end through the real pipeline (2026-10-04; run `g7`, picture `R3i`, `GetFrame` mode 2) - #141 criterion 1
**Read path (new).** No CPU read path exists for DVD slots >= 10 (no `clientMemoryForType` type maps them; GL `read_buffer` reaches a fixed record table), so the real VA flow is used instead: `Tools/userspace/va_capture/comp_run.sh` forwards `declare_image`/`delete_image` (8, 9), stamps (19, 20), `doIDCT` (18) and the type-1 command-buffer submit (`GUARD_FWD_REMAP=1`, write-ahead logged), then `ava_drive --getframe 2` calls AppleVA `DVDDriverGetFrameImpl(dev, frame, buf, rowbytes, mode)` -> ATI VA driver `FUN_00003fc0`, which declares `buf` as an image (`declare_image {0, buf, h*w*bpp}`), submits a DVD record `0x43` (+ register packet: a 3D-engine pass that converts the decoded frame) and the pass writes the converted frame into `buf`. Accepted modes: 2 `yuvs`, 16 `argb`, 32 `rgba`, 64 `ar15` (mode 8 builds fourcc 0x79757634, not accepted -> -5).
**Caller contract (learned the hard way: four kernel panics).** `rowbytes` MUST equal width x bytes-per-pixel (128 for 64 px `yuvs`). The kernel image is declared as height x width x bpp (0x1800 for 64x48x2, pitch 128) but the pass programs its render pitch (`0x138e`) from the caller's `rowbytes`; with 2048 (runs g2/g4/g5/g6) the GPU wrote ~96 KB into the 6 KB image and the G5 panicked with `DART XBE DART out of bounds Exception: PCI0 write logical page 0xC1E000` (0xC22000 in g5): a GPU bus write beyond the mapped image, asynchronous to the submit (the UDP-mirrored log of g6 ends with the second submit returning rc 0). That is a harness bug, not a stock-driver defect; with `rowbytes` = 128 (g7) the call completes (rc 0, exactly 0x1800 bytes written, no panic).
**Result (picture `R3i`: Y blocks flat DC 64, Cb DC 64 + zigzag idx 2 level 40, Cr DC -64 + zigzag idx 1 level 40, MB 0 only).** The output is 4:2:2, **byte order Cb Y0 Cr Y1**, 128 bytes per row, 48 rows. Against `Tools/idct_stream.py` (IDCT + 128, clip): **luma 256/256 exact (136 flat)**; **chroma 256 Cb/Cr samples compared, 234 exact, 22 off by 1, max |diff| 1** (the known +-1 of control bit 16); each 8x8 chroma row serves two output rows (vertical replication 4:2:0 -> 4:2:2); Cb varies with the row (vertical frequency, block 4), Cr with the column (horizontal frequency, block 5) exactly as coded; every uncoded macroblock reads Y = 0 with neutral chroma 128 (written as a whole, as for luma). So the engine decodes Cb and Cr blocks correctly (blocks 4 and 5, after Y0-Y3) and the chroma plane the 3D pass reads is the one the engine wrote.
**Chroma placement.** The kernel's DVD `0x43` handler (`ATIR500DVDContext::process_command_buffer`, `Sources/ATIR500DVDContext_process_command_buffer_Port.cpp`) programs register `0x1150` with the luma base and `0x1151` with `base + (bottom - top rows) x pitch` (plus a 3/2 factor for the second field/plane flag): the chroma plane starts directly after the luma plane at the destination end register (`0x1fe4` = base + height x pitch), i.e. the layout #140 inferred, and the exact chroma values above confirm that this is where the IDCT engine put them.

## 9o. Static analysis of the opcode 0x12 MC-composite record builder (2026-10-05) - what registers it programs, and where a bad reference would surface

Read `ATIR500DVDContext::process_command_buffer` (`Sources/ATIR500DVDContext_process_command_buffer_Port.cpp`, real addr 0x357c0) end to end for the `0x12000000` record-tag branch (the one `g8`/`g10` submit for a forward-predicted macroblock) and cross-referenced every register index it writes against `R3xx_3D_Registers.pdf` (indices are CP type-0 dword offsets, i.e. `MMReg = index << 2`; this was not done in section 9/9m, which only searched the archive for the IDCT-block names at 0x1f80-0x1fff and found nothing - this is a different, 3D-engine register range that **is** documented).

**Registers identified (EXACT, from the archive):**
| dword index (in the record builder) | MMReg | name | role |
|---|---|---|---|
| 0x1150-0x115c (13 writes) | 0x4540-0x4570 | `TX_OFFSET_[0-15]` | texture-unit base addresses (map 0) |
| 0x138a | 0x4e28 | `RB3D_COLOROFFSET[0]` | render-target (destination) base address |
| 0x138e | 0x4e38 | `RB3D_COLORPITCH[0]` | render-target pitch/tiling (same register the GetFrame/0x43 path's `rowbytes` bug writes - see 9l) |
| 0x1393 | 0x4e4c | `RB3D_DSTCACHE_CTLSTAT` | dest-cache control; value 10 = `DC_FLUSH=2, DC_FREE=2` (an ordinary flush+free/purge, not itself anomalous) |
| 0x1087 | 0x421c | `GA_POINT_SIZE` | per-point sprite size for the rasterizer |
| 0x832/0x833 | 0x20c8/0x20cc | `VAP_VTX_AOS_ADDR[0]`/`[1]` | vertex-array-of-structures base address(es) |

**What this confirms about the mechanism.** The composite is a **point-sprite blit**: it sets `GA_POINT_SIZE` to a macroblock-sized sprite, points `VAP_VTX_AOS_ADDR` at a GART-mapped vertex buffer built from the *second* transfer buffer the record references (`self + puVar40[5]*4 + 0x104`, mapped on demand via `map_transfer_to_GART` exactly like `doIDCT`'s own buffers), and binds up to **two sets of four `TX_OFFSET` registers** (`local_b4[0..3]` and `local_a4[0..3]`, each four addresses `iVar18` apart, computed in two 4-iteration loops right before the register writes) as the texture source(s) for the reference-frame fetch - consistent with sampling either four vertically-offset rows of one reference (for half-pel vertical interpolation) or two separate planes (forward + a second reference, matching the record's `fwd`/second-vector motion flags in section 7). The point list itself is walked by a **linked structure with a zero terminator** (`puVar26[0x10]`/`puVar16[0x10]`, the `do { ... } while (*ptr != 0)` loops at lines ~545-563 of the Port file) built from the host macroblock records, and the whole thing ends with `*puVar40 = 0xc00c1000` (closing the sub-stream before `goto LAB_00039028`, the normal continue-to-next-record path - the kernel's CPU-side record walk returns normally in `g8`/`g10`; the hang is therefore in GPU execution of the submitted draw, not in building it, which matches the observed CP ring being fully consumed while `RBBM_STATUS` stays GUI_ACTIVE).

**Where a dangling reference would surface.** Both texture sets and the vertex buffer are resolved through the context's transfer-buffer table (`self + idx*4 + 0x104`) and `map_transfer_to_GART`, exactly like `doIDCT`'s own stream buffers (section 5/9c). If the slot the real VA driver expects to hold the P-picture's reference frame is stale, already freed, or was never re-registered the way the full real decode flow would (our harness drives every picture - including the `I0` reference - through the real `_DVDDriverDecodeImpl` per `gen_ava_vectors.py`'s own docstring, so this is *not* simply "IDCT-only vs composited" as the preceding comment speculated; it is specifically about whatever bookkeeping ties a transfer-buffer-table slot to "the most recently decoded frame" inside the VA driver/kernel), the `TX_OFFSET`/`VAP_VTX_AOS_ADDR` addresses programmed above would point the rasterizer's texture/vertex fetch at the wrong or an unmapped GART page - a textbook "fetch stalls forever" GPU hang, and consistent with the eventual `DART XBE out-of-bounds` page fault recorded at the next boot in both `g8` and `g10`.

**Not established (needs the real client's own packet-builder, `FUN_0000bf20`/`FUN_00008510`'s companion that emits the 0x12 record, not yet disassembled):** which of `puVar40[1]`/`puVar40[5]`/`puVar40[2..c]` is the *reference* image index specifically (vs. the destination or the motion-vector buffer), and therefore whether the harness's `I0`-then-`P2` sequence gives the real client the inputs it needs to compute a valid one. This is the concrete thing to check (by disassembly, not by another live run) before retrying live: find `FUN_0000bf20`'s store into the field that becomes this record's `puVar40[1]`/`[5]`, and confirm it is reading the *same* object/slot our `I0` decode populated.

## 9p. Byte-level comparison of the real captured 0x12 records: `g8` (hangs) vs `g9` (completes) (2026-10-05)

Section 9o was pure static analysis. This section goes back to the raw evidence already on disk - `captures/comp/g8/g8.tsv.mem` and `g9/g9.tsv.mem`, the write-ahead snapshots `run_t3`/`comp_run.sh` already took of the client's type-1 command buffer before each forward/remap - and decodes the actual 0x12 record both pictures wrote, field by field, using the layout read from the real client's record-builder, `FUN_00007850` (`Userspace/ATIRadeonX1000VADriver/ppc/part_001.c:2199`, the function that writes the `0x12000000` tag at `part_001.c:2242` - not `FUN_0000bf20`, which section 4's older note named; that function is just a generic cache-flush helper and the real builder had not been located before now).

**Method.** Each `.tsv.mem` snapshot is a `SNAP seq=N why=... MAP type=1 addr=0x.. dumped=4096 <hex>` line - only the first 4 KiB of the 512 KiB buffer, taken write-ahead before each remap/forward. Matched `g8`'s own "about to remap this exact buffer region away" snapshot (`seq=97`, `addr=0x2088000`) against `g9`'s equivalent (`seq=94`, same `addr=0x2088000`) - the fair comparison point, both runs' *final* client-side state for the same buffer before the kernel ever touches it (an earlier attempt at this comparison used two snapshots that looked alike by sequence number but were not actually the same kind of event in each run - recorded here so a future pass does not repeat it).

**Result - the two records are near-identical except for exactly one region:**
| field (`puVar8[i]`, decoded per `FUN_00007850`) | `g8` (P0: forward MB + residual, hangs) | `g9` (P1: intra only, completes) |
|---|---|---|
| [0] tag+length | `0x12000500` | `0x120003fc` |
| [1]-[5], [0xc], [0xd] | `0,0,0,0,1` / `0,1` | identical |
| [6] (`FUN_00007020` offset A) | `0xed` | `0xed` (same) |
| [7] (`FUN_00007020` offset B) | **`0x28d`** | **`0x20c`** (differs) |
| [8]-[0xb] | `0x90, 0x2, 0, 0` | identical |
| [0xe]/[0xf] (first point-list slot) | **`0x5c8, 0x8000000`** (real content) | **`0x80000000, 0x80000000`** (still the unfilled pad pair) |

Both `[6]` and `[7]` are dword offsets *from the record's own start* that the kernel later computes `puVar26 = puVar40 + 0xed` and `puVar16 = puVar40 + puVar40[7]` from (section 9o's `TX_OFFSET`/`VAP_VTX_AOS_ADDR` writer). At the time of this write-ahead snapshot both target locations still hold the pad word `0x80000000` in both runs (checked directly: words `[rec+0xed-2 .. rec+0xed+6]` and `[rec+0x28d/0x20c-2 .. +6]` are all `0x80000000`), so neither offset is obviously out of bounds or colliding with something already written - the `0xed` vs. differing-but-still-padding `[7]` by itself is not evidence of a bug.

**The one place that *does* carry different real content is `[0xe]/[0xf]`** - the opening pad pair of the per-macroblock point list (`FUN_00007850`'s `*puVar9 = 0x80000000; puVar9[1] = 0x80000000;`, immediately followed by a loop over 24 "slices" at `param_1+0x14428` that calls `FUN_00007490` to overwrite that pair with a real two-word entry whenever a slice has motion data). `g9` (no forward MB anywhere in the picture) never satisfies that loop's gate, so the pair is untouched padding. `g8` (one forward MB) does satisfy it once, and the pad pair becomes `0x5c8, 0x8000000` - the **first and only real point-list entry this capture shows**, and it belongs to exactly the macroblock whose prediction wedges the GPU. `0x5c8` is far too small to be a GART/VRAM address (every real address this project has observed is multi-megabyte), so it reads more like a packed small value - consistent with a macroblock (row, column) position plus flag bits for a point-sprite vertex, but the exact dword layout `FUN_00007490` writes has not been decoded, so whether `0x5c8` is a *correct* encoding of macroblock (0,0) or a malformed one is **not established** - this is the concrete next question, and it is answerable by reading `FUN_00007490` (not found yet in `part_000.c`/`part_001.c`; check `ledger.tsv` for which part file holds it) rather than by another live run.

**What this does and does not narrow.** It rules out "the composite record is shaped differently or skipped for the intra case" (section 9m's framing) - both pictures build a structurally identical 0x12 record through the same code path, with the same control-flow field values (`[2],[3],[4],[0xc]` all equal); the *only* captured difference is the forward MB's own point-list entry, exactly where the mechanism in section 9o says it has to be. It does not yet show whether that entry's content is correct, because the entry's dword format (`FUN_00007490`) has not been read. It also does not rule out something beyond the first 4 KiB of the buffer (the capture tooling's write-ahead snapshots are capped there by design, for crash-safety logging, not full buffer inspection) - a future pass that wants to see the whole record end-to-end would need either a point-list short enough to fit, or an extension to the capture tooling to dump more than 4096 bytes.

## 9q. Correction to 9p after reading `FUN_00007020`: the word-14/15 divergence looks like normal, expected variation, not a malformed entry

9p's claim that word 14/15 is "the forward MB's own point-list entry, written by `FUN_00007490`" does not survive reading `FUN_00007490` itself (`part_001.c:2066`): that function's output is a *fixed* shape (`0x1393,10,0x5c8,0x20000,0x1040,0,...` then a PM4 draw packet) and does not match the captured bytes at that position. **Retracted.**

Reading `FUN_00007020` (`part_001.c:1927`, the function `FUN_00007850` calls to build lists A and B) explains it differently and more mundanely. For list A (`param_3==1`), it does **`_memcpy(param_2, *(param_1+0x15294), *(param_1+0x15298)<<2)`** - i.e. it copies real content, from a per-context pointer/length pair, **directly into `param_2` (= record word 14 onward)**, before appending a fixed 12-word register tail (`0x1144/0x1147/0x1145/0x1146/0x1148/0x1149`, each set from `*(param_1+0x588)`'s picture height - these look like viewport/scissor extent registers, not found in `R3xx_3D_Registers.pdf`) and 30 words of `0x80000000` padding. List B (`param_3==2`) does the analogous thing from a different context pointer/length pair. `puVar8[6]`/`[7]` (`off_A`/`off_B`) are simply the *total lengths* of these two blocks (copied-data length + the fixed 42-word tail), which is why they vary with picture content - not an index/offset bug.

This means **word 14/15 is the first two words of whatever list A's source buffer (`*(param_1+0x15294)` or the `else` branch's pointer) currently holds**, copied verbatim - not a hand-built point-list entry. That source is itself a per-context scratch/template area, almost certainly built or left over from the macroblock/motion-vector processing that happens before `FUN_00007850` is called at all (not yet read). It differing between `g8`'s forward-MB picture and `g9`'s intra-only one is exactly what would be expected if that scratch area holds motion-vector-list state that only exists when a picture has a forward-predicted macroblock - i.e. **this looks like ordinary, correct variation, not evidence of a malformed or garbage entry.** `off_A` (`0xed`) being identical in both runs is consistent with it being a fixed-size template (e.g. a screen-aligned scissor/viewport setup, same for every picture of this size); `off_B` differing by exactly the kind of amount a per-picture motion-vector list would add is consistent with list B carrying that per-picture content.

**Where this leaves #141's criterion 3.** The client-side generation of the composite record, as far as this capture and the three functions now read (`FUN_00007850`, `FUN_00007020`, `FUN_00007490`) can show, looks like it is doing exactly what a correct VA driver would do for a forward-predicted macroblock - nothing found so far points to a harness- or client-side data bug. That leaves the GPU's actual execution of the submitted draw (section 9o's point-sprite/texture-fetch mechanism) as the most likely place the real defect lives, consistent with the project's standing conclusion in section 9n - this pass narrowed *what* gets submitted without finding a flaw in it, rather than finding the flaw. Confirming or ruling that out further would need either a longer capture (the existing write-ahead log caps at 4 KiB per snapshot, not enough to see lists A/B's actual content, which start well past that point for list B) or reading the motion-vector-list builder that feeds `*(param_1+0x15294)`/`+0x1529c` (not yet located), not more reasoning from this capture.

## 9s. Correction to 9r: `RBBM_SOFTRESET` clears the register-level hang but NOT the display - the machine still needs a reboot

9r reported the AMD-documented `RBBM_SOFTRESET` (0x00f0, within the already-proven-safe write_regs mask) as a working, reboot-free recovery from this hang, based on `RBBM_STATUS` reading back to the documented idle baseline (`0x10000140`) after the reset, twice. **Revised conclusion:** `RBBM_SOFTRESET` genuinely clears the CP/VAP-visible busy bits this project can read (useful as a diagnostic - it confirms the stuck unit is reachable by a CP+VAP-only reset, narrowing it away from a pure back-end/GA hang), but it does **not** restore the machine to a usable state. The display compositor stays wedged and a reboot is still required before any further GUI-dependent test (anything using `ava_drive`, which needs a live WindowServer session) can run. ## 9t. Field pictures (criterion 4) - exercised, luma MET against the oracle, chroma has a real unexplained anomaly (2026-10-05)

Unlike the P-picture composite (criterion 3), field pictures are a **client-side `desc[2]` byte** (`picture_structure`, AVA's picture descriptor - see section 4/5: the kext derives `fieldPictureFlag`/`bottomFieldFlag` from it), hardcoded to `3` (frame) in `ava_drive.c`. Added `--pstruct N` (commit b2a8bc7) to override it and ran the already-proven-safe `R3a` picture (one intra MB, DC-only Y0, no motion, no composite - the exact mechanism proven live in sections 9d-9j) through the plain `doIDCT`+`GetFrame` path with `pstruct=1` (top field, run `g13b`), `pstruct=2` (bottom field, run `g13c`) and `pstruct=3` (frame, run `g13d`, a fresh baseline on the same clean boot). All three completed normally (`EXIT=0`, no watchdog, no hang) - this path carries none of criterion 3's risk.

**Luma: MET, byte-exact.** Comparing the frame-mode baseline's source row `k` against the top-field run's physical row `2k` (i.e. assuming the documented doubled-pitch field addressing - section 5: "nonzero doubles the pitch"), **all 8 compared rows match exactly** (`ffffffffffffffff0000000000000000` for the coded/uncoded luma split, identical in every case). The bottom-field run's physical row `2k+1` matches the top-field run's physical row `2k` exactly in all 8 cases too - precisely the "+0x04 bottomFieldFlag: offsets the destination start by one line" behavior documented in section 5, now confirmed with real data instead of just the parameter-block derivation. Field-line addressing for luma works correctly and matches both the already-validated frame-mode oracle and the documented bottom-field offset, in every row checked.

**Chroma: a real, confirmed anomaly - not yet explained.** The same row-doubling check for Cb (`frame` source row `k` vs `top` physical row `2k`) **fails for every odd `k`** (1, 3, 5, 7): those rows read `0x80` (the "untouched" neutral value) where frame mode and the test's own content say the uncoded chroma block should read `0x00` (plain zero, like every other uncoded block in this coded macroblock - section 9f's "uncoded blocks of a coded macroblock are written as 0" rule). Even `k` (0, 2, 4, 6) match correctly. So under field addressing, the chroma plane's own vertical placement introduces an *extra* factor of 2 beyond luma's - every other chroma-replication group lands on the wrong (neighboring/untouched) row instead of the coded block's own value. This is a genuine, reproducible defect in how the engine (or this project's parameter derivation) places chroma specifically for field pictures; it was not visible in any earlier chroma work (section 9l) because that was frame-mode only. Not yet root-caused: candidates are the chroma plane's destination-end/half-height registers (section 2's `0x1fec`/`0x1ff0`) needing their own field-aware halving that isn't happening, or the reverse (an extra halving that shouldn't be there).

**Scope note:** this is independent of `field_dct` (the per-macroblock bit from section 9g/9h, already verified) - `R3a`'s macroblock record has `field_dct=0`; this section is entirely about the picture-level `fieldPictureFlag`/`bottomFieldFlag` addressing, a different mechanism.

**Criterion 4 status:** field picture flags exercised; luma line addressing compared against the oracle and MET (byte-exact, both top and bottom field); chroma field-placement has a confirmed, reproducible anomaly, recorded here rather than further guessed at - whoever next touches chroma+field together should start from this section, not section 9l.

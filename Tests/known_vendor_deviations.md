one that "fixes" it is a divergence to be reported (and then decided on: faithful reproduction is the default, see #73 for the one deliberate beyond-stock item).

## V12: `ATIR5002DContext::process_command_buffer` null-dereferences the per-context "Shared" pointer on a flush with no prior GA-level setup (reproduced, real panic)

**Symptom:** calling the 2D context's flush (`clientMemoryForType` type 0 / `IOConnectMapMemory` memType 0) right after `set_surface` bind, with no other GA-plugin-level setup, panics the stock kernel: `Data access DAR=0x14 PC=...ATIR5002DContext::process_command_buffer+0x3e0`.
Decoded instructions at the fault: `lwz r2, 0x88(r27); lwz r0, 0x14(r2)` - exactly `M<UInt32>(M<SInt32>(self+0x88)+0x14)`, the image-table-count check at the top of the 0x03/0x04/0x08/0x13/0x10 image-record handlers (Sources/ATIR5002DContext_process_command_buffer_Port.cpp). `self+0x88` (the context's `IOATIR500Shared*`) was NULL: the dereference happens unconditionally before the bounds comparison can matter. This was hit live, not synthetically: `Tests/destructive/t3_2d_inject.c` (2026-10-03) opened a 2D connection, bound a 4x4 surface, and flushed (`IOConnectMapMemory` memType 0) - it panicked on **the flush itself**, independent of the hand-built record content, because this connection skipped whatever normal setup (a real GA plugin's own init calls) sets `self+0x88` before any flush. Full panic text: `Tests/baseline/opcode/inject/panic_2026-10-03_t3_2d_inject.log`; `Tools/panic_symbolicate.py` output matches exactly.

**Implication for #42/#45:** this is a real, reproducible STOCK-kernel defect (an unvalidated null the vendor never checks for), not a decompile transcription bug - the ported C++ already has the identical unchecked `M<SInt32>(self+0x88)` pattern, so the rebuilt kext should panic the SAME way given the same misuse, which is the correct parity target. Any further 2D command-stream testing (live or emulated) MUST establish `self+0x88` first (a real GA plugin's context-setup external method, not yet identified by this project) before ever calling a 2D flush, or it will panic every time regardless of record content.

## V13: GL opcode 0x36's handler dereferences and writes through word[1] with no validation (real corruption, deferred panic) - RESOLVED: dead code in the real driver

**Symptom:** injecting a 0x36 record whose word[1] is a value returned by `get_data_buffer` (external method selector 18) does not crash immediately, but the *next* flush on the same connection panics: `Data access DAR=0x8 PC=...IOATIR500GLContext::remove_texture_from_stream+0x1c`, called from `clientMemoryForType+0x4f4`/`+0x84` - a null+8 write, unrelated on its face to the 0x36 record itself. Full log: `Tests/baseline/opcode/inject/panic_2026-10-03_t3_gl_inject.log`.

**Analysis (not yet fully confirmed):** 0x36's handler (`Sources/ATIR500GLContext_process_command_buffer_Port.cpp`) treats word[1] as a `VendorTransferBuffer*` and writes through it unconditionally (`+0x48`, `+0xe`, `+4`, `+0x5c`) with no null/sanity check - the same unchecked-dereference pattern as V12 (2D's `self+0x88`). `get_data_buffer`'s return value (`Sources/IOATIR500GLContext_get_data_buffer_Port.cpp`) comes from a vtable call at offset `0xd0` on a freshly-allocated `IOMemoryDescriptor`-derived object; offset `0xd0` is a plausible slot for a physical/bus-address accessor (e.g. `getPhysicalSegment`), not a dereferencable kernel virtual pointer - a small value like the one observed live (`0xa000`) is consistent with a bus address, not a C++ object pointer. If so, the earlier framing in this file's 0x36 entry ("the client only relays a kernel-issued handle, so it is safe") was incomplete: kernel-issued does not imply validated, and the value's real TYPE (bus address vs. object pointer) was never confirmed before trying it live. **Not yet proven** - needs the real meaning of vtable+0xd0 pinned down statically (or a safer, narrower live/emulated check) before retrying.

**Resolved by re-verifying a fact established earlier the same day, independently of the live crash:** 0x36's only emitter, `FUN_00027150`, is installed into the GLDriver's internal dispatch slot 0x15 only when a context byte at offset `0x2b82` is non-zero (`Userspace/ATIRadeonX1000GLDriver/ppc/part_003.c:5609`). The ONLY store to that byte anywhere in the image (`part_004.c:5863`) unconditionally sets it to 0. **0x36 therefore never runs in real driver usage at all** - unlike 0x2a/0x38/0x3d (the same "statically unreachable" family, but with handlers that only touch PM4-local header words, proven safe to inject with dummy data), 0x36's handler is the one exception whose kernel-side code unconditionally dereferences and writes through word[1] as a real pointer, with no validation. Comparing it to 0x44 (identical dereference pattern, proven safe) was the wrong anchor: 0x44 is safe because real apps constantly exercise it under the right preconditions (a bound texture); 0x36 is simply never reached by anything real, so nothing in the driver has ever had to get this right. The crash's deferred nature (a null+8 fault one flush later, in an unrelated function) is consistent with the unconditional `M<SInt16>(pVVar79+0xe) += 1` write landing on some other mapped low-memory kernel structure without immediately faulting.

**Status:** `Tests/destructive/t3_gl_inject.c` marked HAZARD, do not re-run - there is no real-world scenario this opcode needs to behave correctly for; it is exploitable-by-construction dead code, not a reachable vendor bug. Filed as issue #125, parallel to #124/V12.

## V14: DVD texture-bind opcodes (0x19-0x2a family) null-deref the shared allocator (self+0x84) with no setup - same class as V12, different offset

**Symptom:** injecting any of the DVD texture-bind opcodes (0x19-0x2a, the ones that resolve a texture id into one of the context's 18 bound-texture slots at `self+0x104`) on a connection that never called `declare_image` panics: `Data access DAR=0x14 PC=...ATIR500DVDContext::process_command_buffer+0x1e70`. Decoded: `lwz r9,4(r30); srwi r0,r0,0x18; lwz r2,0x14(r11); cmplw cr7,r9,r2` = `M<UInt32>(M<SInt32>(self+0x84)+0x14) <= puVar40[index]`, the bounds check every opcode in this family does against the shared allocator's texture count BEFORE anything else - `self+0x84` was NULL, giving the same null+0x14 shape as V12 (2D's `self+0x88`). Full log: `Tests/baseline/opcode/inject/panic_2026-10-03_t3_dvd_inject.log`.

**Root cause:** `self+0x84` (`IOATIR500Shared*`) is lazily created only by `IOATIR500DVDContext::declare_image` (external method selector 8) / `create_image` (selector 9) - exact same pattern as 2D's `self+0x88` (#124). This hazard is WIDER than first scoped (`Tests/pm4_opcode_gaps.md`'s original note only flagged the texture-*reading* opcodes 0xb/0xd/0x18/0x43/0x44): every opcode in the 0x19-0x2a texture-*binding* family does this same check and will panic identically on an unprepared connection.

**Caught too late by the emulator, for a known reason:** `Tools/userspace/emu/kemu.py`'s sweep marked 0x19-0x2a as clean because the harness never populated `self+0x84` either - Unicorn auto-zero-fills the unmapped read instead of faulting, exactly the documented blind spot (see V13's writeup), and it bit the same way here.

**Status:** `Tests/destructive/t3_dvd_inject.c` marked HAZARD. Fix (same pattern as #124): call `declare_image` to establish `self+0x84` before any opcode in this family. Not yet re-attempted live.

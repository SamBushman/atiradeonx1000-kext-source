# Real-consumer scenarios for the feature-parity suite (issue #42 criterion 3) - definition and stock status

The three real userspace consumers of the kext are WindowServer / Quartz (2D context + Surface), OpenGL applications (GL context), and video playback (DVD context through the VA driver).
This file defines, for each, the scenario, what is recorded on the **stock** kext today, what a rebuilt-kext run (#45) must reproduce, and what is still missing. Nothing here loads the rebuilt kext.

## Opcode-level coverage (criterion 2, second half)

`Tests/pm4_opcode_inventory.md` (generated by `Tools/opcode_inventory.py`) lists the opcodes each `process_command_buffer` handles: GL 66, DVD 62, 2D 17. Which of them a real workload actually emits is
**not yet measured**. The two observation points that exist today:

1. The GPU command ring (IOKit memType 2) at a chosen moment (`ringdump.sh`, needs the Tiger gdb-696 technique in `tiger-ssh`): this is the PM4 stream the kext *produced* from the opcodes, so it shows the output of
   `process_command_buffer` rather than its input.
2. The per-context command buffer the client writes (the dispatchers' input) is mapped by the kext through `ClientMemoryForType` and can be mapped by a recorder the same way the ring is. A recorder that snapshots it at
   each flush and tallies the top byte of every command word would give the opcode histogram per workload. **This recorder does not exist yet**; building it is the next step for criterion 2, and the first
   thing to find is which call tells the kernel to process a buffer (none of the 21 GL external methods is a "submit").

## Pass/fail definition for a scenario (used by the parity report)

* The sequence of (connection type, selector, return code) per connection equals the stock capture, after dropping values that are machine state (addresses, stamps; see `Tests/known_vendor_deviations.md`).
* No panic, hang, or visible drawing difference; for GL, equal pixel checksum and an identical ring.
* `Tools/parity_report.py` produces the verdict for the destructive-protocol logs; the scenario captures are compared with `analyze_capture.py` output and `diff`.
